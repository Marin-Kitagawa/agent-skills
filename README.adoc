= Agent Skills Collection
:toc: left
:toclevels: 3
:sectnums:
:icons: font
:experimental:

A curated, versioned collection of *207 agent skills* spanning scientific research, engineering, data analysis, design, software, and media production. Every skill is a self-contained package with its own `SKILL.md` instructions, supporting references, scripts, and assets. Each skill is committed and released independently with a signed Git commit and a signed annotated tag.

The collection is designed to be cloned directly into an agent skill directory (for example `~/.agents/skills`), where compatible agents discover skills by reading each package frontmatter.

== At a Glance

[cols="2,5",options="header"]
|===
| Property | Value

| Skills | 207
| Categories | 18
| Tracked skill files | 3375
| Skill content size | about 46.5 MB
| Default branch | `main`
| Origin | `https://github.com/Marin-Kitagawa/skills-manager-backup`
| Release model | One commit and one signed annotated tag per skill
| Package format | Folder per skill with a YAML-frontmatter `SKILL.md`
|===

Each skill folder is independent: it can be copied, installed, or checked out from its tag without pulling unrelated skills.

== Repository Layout

[source,text]
----
skills/
  <skill-name>/
    SKILL.md              # Frontmatter + operating instructions (required)
    references/           # Optional deep-dive documentation
    scripts/              # Optional helper scripts and tests
    assets/               # Optional templates, fonts, fixtures
    ...                   # Any other supporting files the skill needs
----

`SKILL.md` begins with a YAML frontmatter block. The commonly used fields are:

[cols="2,6",options="header"]
|===
| Field | Purpose

| `name` | Machine-readable skill identifier, normally matching the folder name.
| `description` | What the skill does and when an agent should load it.
| `license` | License terms for that skill package.
| `compatibility` | Runtime, dependency, credential, or network requirements.
| `metadata` | Optional author, version, review date, and provenance fields.
| `allowed-tools` | Optional tool allowlist used by some agents.
|===

Supporting files are not decoration: many skills contain executable Python, Node.js, shell, or HTML/JavaScript that the agent is expected to run. Review them before use.

== How Skills Are Consumed

Agents that support the `SKILL.md` convention scan a skills directory, read each frontmatter `description`, and load the full `SKILL.md` only when a task matches. A typical setup:

[source,bash]
----
git clone https://github.com/Marin-Kitagawa/skills-manager-backup.git ~/.agents/skills
----

Or copy only the packages you need:

[source,bash]
----
cp -R scanpy ~/.agents/skills/
----

The exact discovery path depends on the agent runtime. Some clients read `~/.agents/skills`, others use a project-local `.agents/skills` directory or a configured path. Keep the folder name and the frontmatter `name` unchanged to avoid ambiguous skill identities.

Skills are instruction packages, not standalone applications. They assume the agent has tools for reading files, running commands, and (where documented) accessing the network.

== Requirements and Compatibility

There is no single runtime for the whole repository. Compatibility is declared per skill in its frontmatter and repeated in the body:

* *Python skills* typically expect Python 3.10-3.13, `uv` or `pip`, and the packages named in the skill (for example `scanpy`, `pymc`, `rdkit`, or `aeon`). Some pin exact upstream versions.
* *JavaScript and video skills* typically expect Node.js 20+ and may invoke FFmpeg, Chromium, or a HyperFrames CLI.
* *Hosted and credentialed skills* require API keys or accounts for services such as Benchling, DNAnexus, Latch, Tamarind, Rowan, Adaptyv, Ginkgo, Figma, or OpenRouter.
* *Cloud and infrastructure skills* may require provider CLIs, containers, GPUs, or platform-specific utilities.
* *Data-access skills* often need network access; several also require citations or license compliance for the underlying datasets.

Always read the `compatibility` field and the "Requirements" or "Setup" section of the specific `SKILL.md` before running a skill.

== Versioning and Signed Releases

Each skill has its own history:

* One signed commit stages and adds that single folder.
* One signed annotated tag, named exactly after the folder, marks the release.
* The full catalog therefore has 207 commits and 207 skill tags, plus this README commit.

Inspect or verify a release:

[source,bash]
----
git tag -l
git tag -v scanpy
git show scanpy --stat
git checkout scanpy -- scanpy/
----

Tags are signed with the maintainer GPG key. Verification requires the corresponding public key in the local keyring. Commit signatures use `git commit -S` and can be checked with `git log --show-signature`.

== Security and Responsible Use

* Skills can instruct an agent to execute code, install packages, access local files, and call external services. Treat a skill as executable supply chain content, not passive documentation.
* Review `SKILL.md` and any scripts before first use, especially for skills that handle credentials, clinical data, laboratory devices, or destructive operations.
* Credentials should be supplied through environment variables or a secret manager. Do not paste keys into prompts, commit them, or store them in skill folders.
* Clinical, pharmacological, and laboratory skills are research aids only. They do not replace qualified professional review, regulatory approval, or device safety validation.
* Hosted services and datasets carry their own terms. Check the provider terms and dataset licenses before submitting data or publishing results.
* No repository-wide warranty is provided. Outputs must be validated for the intended scientific, engineering, or production context.

== Adding or Updating a Skill

A new skill should:

. Use a unique lowercase folder name and a matching frontmatter `name`.
. Explain *what it does* and *when to use it* in the first lines of `description`.
. State runtime, dependency, credential, and licensing constraints explicitly.
. Put long documentation in `references/`, executable helpers in `scripts/`, and templates or fixtures in `assets/`.
. Be self-contained: avoid absolute paths and machine-specific assumptions.
. Be tested from a clean environment when it includes runnable code.

This repository follows a one-skill-per-commit convention:

[source,bash]
----
git add -- <skill-folder>
git commit -S -m "feat(skills): add <skill> skill"
git tag -s <skill-folder> -m "Release of the <skill> skill."
git push origin main --follow-tags
----

Updates to an existing skill may reuse the same convention or use a focused conventional-commit message, for example `fix(<skill>): ...`. Avoid mixing unrelated skills in one commit so the per-skill tags remain meaningful.

== Provenance

Skills were assembled from a working agent skill library and preserve their original frontmatter, references, scripts, and license notices. Many packages identify their author or upstream project in `metadata`. Where a skill wraps an upstream library or service, the authoritative documentation remains the upstream project; this repository provides agent-facing integration guidance.

Corrections, additional references, and compatibility updates are welcome as focused commits.
